# Open-MOPD step pipelining

The native Open-MOPD run (`skyrl-train/ci/opd/open_mopd_native_full.py`) matches the published scores at step 32 but
spends about 3.2 times the wall clock per optimizer step of the authors' colocated `verl` control on the same
H100x8 node. This document fixes the shared vocabulary, the launcher option surface, the constraints each variant
must respect, and the measurements that decide between them, so that the colocated and fully asynchronous
implementations can land as separate pull requests without diverging.

## Problem

The native run partitions one node statically: four FSDP2 learner GPUs, one to four vLLM rollout engines, and three
pinned vLLM teachers (one per domain). The synchronous trainer runs generation, teacher and student scoring, and the
policy update one after another. Every phase uses only its own slice of the node.

| Phase (native "fast" run, steps 22–33) | Mean seconds | GPUs busy |
| --- | ---: | --- |
| generation | ~1,000 | rollout engines |
| teacher and student scoring | ~760 | teachers (+ learner student forward) |
| policy update | ~430 | learner |
| inline AIME validation + full checkpoint (even steps only) | ~1,700 | rollout engines, learner |
| authors' `verl` control, whole step | ~940 | all eight |

Student-training MFU over a whole native step is 0.78%. Over the update phase alone it is roughly 11%. The learner is
not the bottleneck; the step shape is. Evidence: marin issue #9250, timing and MFU comment.

## Two ways to fill the node

**Colocated.** Every phase gets all non-teacher GPUs. The rollout engines and the learner share GPUs and time-share
them with vLLM sleep/wake (`trainer.placement.colocate_all=true`). Phases stay sequential and on-policy; each phase
gets shorter because it has more GPUs. Cost: weight offload and reload at each phase boundary, and memory headroom
for the learner beside the engine's KV cache. This is what the authors' control does.

**Fully asynchronous.** Keep the static partition, stop waiting. Rollout workers generate group N+1 while the learner
updates on group N and the teachers score whatever has arrived (`FullyAsyncRayPPOTrainer`). Per-batch latency is
unchanged; throughput rises because three batches are in flight. Cost: rollouts are generated by a policy up to
`max_staleness_steps` optimizer steps behind the learner, which the clipped surrogate and truncated importance
sampling must absorb.

The two are **mutually exclusive today**: `FullyAsyncRayPPOTrainer.__init__` asserts `colocate_all` is false.
Neither pull request lifts that assertion. Composition (colocated rollout and learner, asynchronous teachers) is a
follow-up once each variant has a measured baseline.

## Launcher option surface

Both variants are options on the existing launcher (colocated: #709, fully asynchronous: #710) and default to today's behavior. The Hydra overrides for the
default remain byte-identical to `main` so the existing contract tests keep passing unchanged.

```
open_mopd_native_full.py [--placement {partitioned,colocated}] [--schedule {sync,fully_async}]
```

- `--placement partitioned` (default): current static partition.
- `--placement colocated`: policy, reference, and rollout engines share the non-teacher GPUs; teachers stay pinned.
- `--schedule sync` (default): `RayPPOTrainer`, 1,024-prompt rollout batches, 256-prompt minibatches.
- `--schedule fully_async`: `FullyAsyncRayPPOTrainer` with the step accounting below.
- `--placement colocated --schedule fully_async` is rejected at argument parsing with the assertion's reason.

Each option contributes its overrides through its own helper that returns a tuple appended to the base argument
list. Neither helper restructures `hydra_arguments()`; that keeps the two diffs additive and the merge trivial.

## Invariants both variants keep

These are the method, not the cost. Neither variant changes them:

- objective `student_topk_policy_surrogate`, `reward_mode=replace`, coefficient 1.0, top-16 after nucleus 0.99;
- routing plan `opd` with one pinned local vLLM teacher per domain, `student_selected_topk` evidence;
- domain gradient balance: equal target shares, gap-following alpha 1.0;
- four optimizer updates per 1,024 prompts (see step accounting), one PPO epoch, learning rate 1.5e-6, clip 0.2/0.28;
- the pinned student, teachers, dataset digests, and 16,384-token response cap;
- every optimizer checkpoint retained (`max_ckpts_to_keep=-1`) so independent evaluation can pick any step.

## Constraints on the fully asynchronous variant

Facts from `skyrl_train/fully_async_trainer.py`, `entrypoints/fully_async.py`, and
`config/trajectory_runner_capabilities.py` at `main` 401a2bc5:

1. `train_batch_size` must equal `policy_mini_batch_size`. The synchronous run does 200 steps of 1,024 prompts with
   four 256-prompt updates each. The asynchronous run therefore uses `train_batch_size=policy_mini_batch_size=256`
   and `max_steps=800`; checkpoint, HF export, and evaluation intervals scale from 2 to 8 so cadence per prompt is
   unchanged. `global_step` counts optimizer updates in both trainers; the report must state that async step 8
   corresponds to sync step 2.
2. `generator.batched=false`, `generator.async_engine=true`, `colocate_all=false`.
3. `num_parallel_generation_workers >= policy_mini_batch_size`. Start at `256 * (max_staleness_steps + 1)`, the
   example's convention.
4. Staleness. `max_staleness_steps=1`. No behavior-policy correction reaches the distillation loss at all: under
   `reward_mode=replace`, `compute_policy_objective` skips the TIS-capable policy loss, and the distillation
   objectives take `old_action_log_probs` (the learner's pre-update forward) as the behavior term, never the
   rollout engine's `rollout_logprobs` (`skyrl_train/distillation.py`, `sampled_reverse_kl_loss` and the student
   top-k surrogate). Independently, `validate_cfg` requires full-distribution sampling for `use_tis` and the recipe
   samples with nucleus 0.99. So the clipped surrogate against the learner's own pre-update logprobs is the only
   guard against stale rollouts, which is why the bound is one update, why the first asynchronous run must be
   compared against a synchronized baseline at matched prompt count, and why raising the bound needs a separate
   validation of the behavior denominator, per-turn policy-version provenance, and ratio tails, not a config change.
5. Trajectory runner. The existing `skyrl_train.entrypoints.fully_async` pairs the asynchronous trainer with the
   HTTP-backed SkyRL Gym runner. That runner's plain chat path re-tokenizes text and returns no logprobs and no
   student top-k candidates (`OpenAIHTTPModelClient.generate`, `token_provenance=RECONSTRUCTED`), and the entrypoint
   requires an HTTP endpoint and a custom chat template. `student_selected_topk` evidence needs the student's exact
   top-16 ids and behavior logprobs from the rollout, which only the in-process `DirectModelClient` path returns.
   The asynchronous variant therefore adds an entrypoint that pairs `FullyAsyncRayPPOTrainer` with the same
   in-process SkyRL Gym runner the synchronous run uses (capability mode `SKYRL_GYM`: exact sampled completion,
   runtime-validated action tokens). `entrypoints/terminal_bench.py` already pairs the asynchronous trainer with a
   non-HTTP runner, so this follows an existing pattern rather than adding a new one. The capability validator
   gains a rule that `student_selected_topk` evidence requires exact sampled completions, so the HTTP entrypoint is
   rejected before Ray starts instead of failing at the first teacher request.
6. Teacher scoring queues: `trainer.fully_async.teacher_scoring.max_queued_per_teacher` and `workers_per_teacher`
   bound work per logical teacher. Defaults (8, 1) are the starting point.
7. Prompt order. The schedule parquet is pre-weighted 2:2:1 and read with `data.shuffle=false`. The asynchronous
   dataloader iterates prompts individually in file order, so any 1,024-prompt window keeps the mix; the domain
   gradient balancer runs per 256-prompt batch. This is a change in balancing granularity and is recorded as such.
8. Resume uses the asynchronous generation-buffer checkpoint (`docs/design/fully-async-resume-uid-ownership.md`).
   The launcher's `--resume` identity check gains the schedule so a synchronous run cannot be resumed as an
   asynchronous one.

## Constraints on the colocated variant

Facts from `config/ppo_base_config.yaml`, `marinskyrl/distillation.py`, and `docs/algorithms/opd.rst`:

1. `colocate_all=true` requires `generator.run_engines_locally=true` and a `gpu_memory_utilization` that leaves room
   for the FSDP2 learner's parameters, gradients, and optimizer state next to the engine's KV cache during
   generation. The learner offload timers (`offload_policy_model_to_cpu`, `backload_policy_optimizer_to_gpu`) already
   exist; vLLM sleep and wake have no timer and get one if cheap.
2. Teachers keep `placement=pinned` on their own GPUs. `TeacherPlacement.CO_RESIDENT` and `TeacherSource.RESIDENT`
   are typed but not served by the runtime; making teachers share the pool is stage 2 and only if contained.
   `rotating` placement (three teachers through one drained residency slot) is served and is the cheaper way to
   free GPUs if stage 2 does not land.
3. Pool sizing. The colocated PR (#709) uses the five-GPU pool with all three teachers pinned
   (`policy_num_gpus_per_node=5`, `num_inference_engines=5`, TP 1). Sharing GPUs with teachers is not a contained
   change: `validate_distillation_runtime_support` rejects `CO_RESIDENT` and `_start_local_teacher_pool` launches
   teacher engines with `inference_engine_enable_sleep=False`, so it needs a teacher lifecycle and a shared
   placement-group design first. Rotating teachers (a seven-GPU pool) is the follow-up if the five-GPU pool leaves
   the update phase short of memory or compute.
4. Weight sync after each update goes engine-to-engine on the same GPUs; the `sync_weights_to_inference_engines`
   timer captures it. The colocated PR adds `timing/inference_engine_sleep` and `timing/inference_engine_wake`
   around the synchronous trainer's engine transitions.

## Measurement plan

Baseline first, on the current configuration, twelve steps (six odd, six even) after warm-up. Then one variant at a
time on the same window. Every number below is already logged unless marked.

| Signal | Source | Expected effect: colocated | Expected effect: fully async |
| --- | --- | --- | --- |
| scored response tokens per GPU-second | `distillation/scored_tokens` ÷ (8 × `timing/step`) | up | up |
| `timing/generate` | trainer timer | down (more engines) | unchanged per batch |
| `timing/policy_train` | trainer timer | down (more learner GPUs) | unchanged |
| `timing/wait_for_teacher_evidence` | trainer timer | unchanged | down (scoring overlaps) |
| `timing/offload_policy_model_to_cpu`, `backload_policy_optimizer_to_gpu` | trainer timer | appear; must stay a few percent of step | absent |
| `timing/inference_engine_sleep`, `timing/inference_engine_wake` | added by the colocated PR | appear; must stay a few percent of step | absent |
| `timing/save_checkpoints` (blocking snapshot) and `timing/checkpoint_upload` (background) | #711 splits the save; the marker is committed after upload | blocking part drops to the local snapshot on even steps | same |
| optimizer steps per hour | `global_step` over wall clock | up | up |
| off-policy staleness | Grafana `rl_runs` "Off-policy staleness" | zero | bounded by `max_staleness_steps` |
| `generate/tis/*` alignment | rollout metrics | unchanged | exact-match fraction stays ~1.0 |
| inline AIME at matched prompt count | `validation/<step>.jsonl` | unchanged | unchanged within noise |
| per-GPU utilization by role | not logged at GPU granularity; Iris gives node level | learner and rollout GPUs busy in every phase | every role busy across batches |

Decision gates, in order:

1. Tokens per GPU-second must rise. If it does not, the timer that moved was not on the critical path and the
   variant is not adopted.
2. Inline AIME at matched prompt count must stay within noise of the baseline. A shift means the variant changed
   the recipe, not its cost; for the asynchronous variant that is the staleness signal and the answer is to lower
   `max_staleness_steps`, not to accept the shift.
3. Whichever variant wins becomes the default in the launcher; the other stays available for the composition work.

## Out of scope

Sample packing, evidence-assembly vectorization, teacher prefill chunk size, and evaluation cadence are separate
changes (marin issue #9250 efficiency list, items 2 through 5). They apply to both variants and are measured on top
of whichever wins. Background checkpoint upload (#711) is the checkpoint half of item 2: ranks still stage their
shards synchronously, the cloud upload runs single-flight in the background, colocated inference residency is
restored before the upload completes, the `latest_ckpt_global_step.txt` marker is committed last, and the fully
asynchronous shutdown drains the pending upload. The inline AIME evaluation on the same cadence remains on the
critical path until it moves to its own Iris job. The issue's timing data gives even steps about 1,700 s over odd
steps for checkpoint plus evaluation together and does not split the two; the first baseline run must report
`timing/save_checkpoints` and `timing/eval` separately before either change is credited.
