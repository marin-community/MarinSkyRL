# Exact delta weight updates in current RL systems (2026-09-20)

## Summary

The published systems offer one plausible change for MarinSkyRL's **remote** case: keep the acknowledged image on CPU and stream exact XOR bytes through lossless compression while the inference engine continues useful work. NeMo RL implements the CPU or mmap baseline, bounded pipeline, S3 or ZeroMQ transfer, and acknowledgement-backed commit. Slime, vime, and miles implement a related disk delta with host-local checkpoint reconstruction. A two-task H100 S3 probe below qualified exact acknowledged updates and measured a smaller object than GPU indices, but it is neither a full-model Grug run nor a cross-region result.

No surveyed system demonstrates a faster replacement for MarinSkyRL's **same-datacenter direct expert path**. VERL's large gains include removing a full trainer gather that MarinSkyRL's direct expert-owner route already avoids. AReaL's AdamW inversion removes a stored baseline in some configurations, but still reconstructs and compares each element, adds distributed work, and its current source explicitly handles observed BF16 false negatives for router weights by sending those tensors dense. vLLM and SGLang expose receiver and transport hooks; they do not by themselves find changed elements. Dense publication remains MarinSkyRL's production default while the candidate is measured.

The comparison below describes inspected source at pinned revisions, not an endorsement of a system's public speedup for the Grug topology. The live main heads were checked on 2026-09-20. The VERL, NeMo RL, miles, and vLLM files cited below were unchanged between the local inspected revisions and those heads.

## Candidate gate

**Select one remote candidate:** an acknowledged CPU baseline with exact XOR plus zstd and bounded stage overlap, based on NeMo RL's implemented path. It could remove MarinSkyRL's 8.179 GB GPU base per sender root and lower cross-region bytes where the [#698 one-object relay](https://github.com/marin-community/MarinSkyRL/issues/698) showed transfer cost was material. Compare it against dense and GPU indices with the same BF16 source/target bits, bucket size, backend, and update schedule. The first screen must measure D2H, CPU compare/XOR, compression, transfer, decompression, H2D/apply, commit, peak CPU/GPU memory, and useful overlap. The public NeMo architecture alone cannot predict a win.

Do not prototype AdamW inversion as an exact shortcut yet. It still scans converted weights, needs optimizer-specific inverse and extra reductions, and the Qwen3 router exception has not been qualified against Grug's BF16 source and FP32 installed router. Do not prototype VERL's sparse gather here: MarinSkyRL's expert sender already holds the complete routed matrix and broadcasts it directly to only its destination group, so removing a rank-0 full gather cannot yield VERL's reported gain. vLLM's new sparse backend uses the same index/value representation and leaves detection to the caller. Slime/vime/miles disk reloads are a separate remote topology and duplicate NeMo's CPU baseline question.

The CPU remote candidate passed the small-scale gate below: raw BF16 edge words survived two updates, a wrong base version was rejected, and a separate-task same-region S3 relay installed and acknowledged six exact updates per arm. Its measured advantage is topology-specific and synthetic. A material cross-region full-model transfer needs Romain's go-ahead under the goal's constraint. No production switch follows from this probe.

## One-H100 mechanism screen

`scripts/bench_cpu_xor_delta.py` generated independent source and receiver BF16 tensors on one H100. Its CPU qualifier covers two acknowledged updates with raw NaNs, infinities, subnormals, and both zero signs; it rejects a wrong base version. The timed screen used representative 3.277M and 6.554M-value expert matrices plus a 67.109M-value (128 MiB) bucket, densities 0.1%, 0.5%, 1.4%, 1.9%, and 2.4%, and three synchronized repeats per condition. The source flips low bits at selected positions, so its zstd ratio is an optimistic pattern; the distributed experiment below uses random nonzero XOR words. No network or useful overlap is in this screen.

| 128 MiB bucket, median of three | GPU index bytes | CPU XOR/zstd bytes | GPU index local path | CPU XOR local path |
| --- | ---: | ---: | ---: | ---: |
| 0.1% changed | 0.404 MB | 0.110 MB | 0.58 ms | 14.42 ms |
| 1.4% changed | 5.638 MB | 1.114 MB | 0.68 ms | 30.95 ms |
| 1.9% changed | 7.653 MB | 1.445 MB | 0.70 ms | 40.35 ms |
| 2.4% changed | 9.664 MB | 1.761 MB | 0.72 ms | 47.39 ms |

At 1.9%, the 3.277M and 6.554M-value shapes took 0.17/1.46 ms and 0.19/2.58 ms for GPU-index/CPU-XOR respectively. For the 128 MiB bucket, CPU D2H, change detection, pack, compression and receiver apply medians were 2.67, 10.12, 10.28, 4.04 and 0.24 ms. The CPU design replaces a 128 MiB GPU baseline with a 128 MiB pinned host baseline and a bounded 128 MiB staging buffer in this probe. The combined probe reported 87.5 MB transient GPU allocation above the already allocated tensors at 1.9%; host peak RSS was not captured. The initial NumPy detector was slower and less faithful to NeMo RL's Torch CPU detector, so the corrected Torch/gap-codec result is decisive; the initial artifact remains retained as diagnostic history.

## Matched same-region S3 relay

`scripts/bench_cpu_xor_relay.py` ran one H100 source task and one H100 live receiver task in separate pods on `cw-rno2a`. Each arm used identical 128 MiB raw BF16 starting bits, six successive updates at 1.9% changed density, random nonzero XOR words, one object per update, and an acknowledgement before source baseline commit. The receiver independently regenerated each dense target and compared every installed raw word. All arms' six target SHA-256 hashes match. The first update is excluded from timings. The CPU XOR arm uses a pinned CPU baseline, Torch CPU bit comparison, gap-coded locations, XOR words and zstd level 1. GPU indices use the acknowledged GPU base and int32 positions plus BF16 replacements; dense sends the complete BF16 image. The receiver applies each to a live GPU tensor. This matches the source bits, object backend, receiver hardware, update order and verification contract across arms, but it is a synthetic single bucket with sequential S3 objects and no trainer or rollout work.

| Arm, five post-warmup updates | Object/update | Median source local stages | Median S3 put | Median acknowledged interval | Median receiver apply |
| --- | ---: | ---: | ---: | ---: | ---: |
| Dense | 134.218 MB | 0.136 s | 0.653 s | 2.846 s | 0.037 s |
| GPU indices | 7.650 MB | 0.003 s | 0.314 s | 2.081 s | 0.002 s |
| CPU XOR/zstd | 3.996 MB | 0.029 s | 0.281 s | 1.238 s | 0.002 s |
| CPU XOR/zstd, repeat | 3.996 MB | 0.035 s | 0.314 s | 1.568 s | 0.002 s |
| GPU indices, repeat | 7.650 MB | 0.003 s | 0.311 s | 2.077 s | 0.002 s |

The repeat timed the successful S3 GET separately: 0.156 s median for the 3.996 MB XOR object and 0.866 s for the 7.650 MB index object. The original receiver `wait_get` also includes source preparation and polling, so it must not be presented as a pure transfer timer. The acknowledged interval includes put, receiver work, a small acknowledgement object and 200 ms polling granularity. The first GPU-index receiver failed before applying an update because `index_copy_` required int64 indices; a corrected receiver consumed the still-running sender's first object, and all six subsequent version/byte checks succeeded. This is a prototype type error, not a transport failure.

The same-region S3 object path favored CPU XOR in these runs, but two short trials per sparse arm do not establish a production throughput gain. The source uses random raw BF16 starting words and random XOR values, not measured Grug weight-change values; the exact object-size ratio may differ. This experiment did not exercise a remote region, full model, pipeline overlap, nonexpert weights, or fully asynchronous trainer/rollout work. Its GET difference is specific to the S3 endpoint and object sizes measured here; it cannot be assigned to NCCL, NIXL, TCP, or cross-region transfer.

## Decision and remaining gate

**Retain** dense as MarinSkyRL's production default and exact GPU sparse indices as a run-level opt-in for direct expert publication. The external audit found no justified replacement for that same-datacenter path; #698's corrected Grug comparison shows a large byte reduction without a demonstrated useful-throughput gain. **Do not switch** the direct path to CPU XOR: at 128 MiB and 1.9% changes it adds roughly 40 ms of local work before transport, while the GPU index path takes below 1 ms in the one-H100 screen.

**Consider a separate CPU-owned exact remote publisher** only for a topology where GPU baseline memory or object bytes are material and useful work can overlap CPU preparation. It has passed small exactness and same-region object gates, not a full Grug or cross-region gate. The smallest coherent follow-up is one experimental publication strategy behind the existing boundary, with bounded CPU stage/encode, receiver version check and exact live apply, global acknowledgement before baseline commit, and a known-good reload after uncertain partial apply. Compare it with dense and GPU indices under one resolved full-model async recipe before production adoption. Do not add an adaptive selector or change default routing.

The full-model remote launch is not presently an existing config switch. [`ExpertBlockSync`](https://github.com/marin-community/MarinSkyRL/blob/78602a81ecfefc5b9d551e1385536fa0f951ea4f/skyrl-train/skyrl_train/weight_sync/expert_block/driver.py) binds trainer and receiver participants into one NCCL rendezvous inside the Ray job. [`RemoteInferenceEngine`](https://github.com/marin-community/MarinSkyRL/blob/78602a81ecfefc5b9d551e1385536fa0f951ea4f/skyrl-train/skyrl_train/inference_engines/remote_inference_engine.py) can generate over HTTP, but its weight loader still requests a distributed broadcast group; it has no object-delta receiver for the live Grug expert views. A cross-region fully asynchronous trial first needs a bounded experimental object publisher and live receiver endpoint, plus resolved remote placement, pause/resume and failure behavior. The same-region probe supplies codec and protocol evidence; it does not qualify that integration.

A material 25-update cross-region Grug comparison remains a separate decision. Naively scaling #698's routed-expert payload and the measured random-XOR ratio gives about 130.86 GB dense, 7.34 GB GPU indices, and 3.84 GB CPU XOR per update; three 25-update arms would write roughly 3.55 TB of expert objects and read the same again. This is a planning estimate, not a validated remote payload: a canonical remote layout, nonexpert tensors, replication and concurrency could change it. [CoreWeave's current public pricing](https://www.coreweave.com/pricing) lists no internal transfer or object request fee, hot object storage at $0.06/GiB-month, eight H100s at $49.24/hour and four GB200s at $42/hour. Five H100 nodes plus two four-GB200 groups would list near $330/hour; three 10–20 minute arms imply roughly $165–$330 of GPU time before account-specific rates, extra preparation, storage retention or retries. This run would resolve whether the single-bucket relay effect survives actual cross-region transfer and fully asynchronous useful work. It requires Romain's go-ahead under this goal's constraint.
