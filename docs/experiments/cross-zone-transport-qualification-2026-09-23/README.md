# B200 to H100 cross-zone transport qualification

## Current result

Cross-zone host-memory InfiniBand is **unqualified**. The same 1 KiB RDMA write test passed between two GB200 hosts in `cw-us-east-08a`. From a GB200 in that zone to an H100 in `cw-rno2a`, a checksum-verified 1 MiB TCP transfer passed, but the RDMA client completed zero writes and reported status 12, syndrome `0x81`. The hosts exchanged RDMA connection metadata over TCP before the failure. This separates ordinary host routing from RDMA completion on the tested HCA/GID; it does not prove that CoreWeave offers no supported cross-zone RDMA configuration.

Two 12-version host-memory comparisons on the **same physical host pair** changed order between job windows. In the first, object delivery had a 1.385 s median versus 25.204 s for TCP. In the second, TCP had a 1.271 s median versus 1.365 s for object and won 7 of 12 pairs. All receiver hashes matched. The first TCP slowdown did not persist, and its cause is unknown. **There is no stable TCP-versus-object winner.**

NCCL Socket was the fastest **observed** GPU path on that fixed pair: 0.497 s median for 11 warmed 300 MiB, 32-chunk broadcasts to one H100 GPU, and 0.558 s median for four warmed broadcasts acknowledged by two H100 GPUs on one host. Those GPU bytes were not paired with the host-memory runs; the communicator was fixed and neither model-tensor apply nor asynchronous Grug was timed. This is a promising bounded delivery result, not a production strategy verdict.

### Calibration and paired comparison

The two-repeat 300 MiB [calibration](raw/calibration/sender-result.json) tried one or four persistent TCP streams, requested default or 4 MiB socket buffers, and four, 16 or 32 concurrent object PUTs/GETs. Four TCP streams and 32 object streams each delivered in about 1.2–1.6 s on GB200 `s90vxs64` → H100 `g5ba7d4`. The TCP sockets persisted across conditions, so later “default buffer” rows inherited earlier buffer changes. This prevents a clean buffer-size conclusion. The comparison froze **four persistent TCP streams with requested 4 MiB send/receive buffers** (Linux returned 8 MiB) and **32 concurrent object requests**. Calibration jobs: `/romain/cross-zone-qual-east-calibration-20260923` and `/romain/cross-zone-qual-rno-calibration-20260923`.

Each paired version uses the same 32 ordered chunks and fresh 300 MiB of incompressible content for both methods. Object keys are unique per version and method; method order alternates. The timer ends only when the H100 returns the SHA-256 acknowledgement. All 24 versions × 2 methods matched the receiver result and the separately retained H100 file. The [analyzer](../../../scripts/analyze_cross_zone_qualification.py) checks the pairs and reports the median and observed range, without calling 12 samples a p95.

### Full-update size implications (model only)

The 300 MiB prefix is about 3.85% of one root's dense routed experts. The options below change the payload before any transport is selected; these are **not** measured full-update delivery times.

| Expert payload per root | Bytes | Other measured or modeled cost |
| --- | ---: | --- |
| Dense BF16 | 8.179 GB | Existing #698 global dense total divided by 16 unique roots. |
| GPU sparse index/value at median 1.870% density | About 459 MB | `3 × density × dense BF16 bytes`; omits headers and nonexpert tensors. #698's sender prior-image baseline cost is 8.179 GB per root. |
| CPU random-XOR compressed packet | About 240 MB | Size is inferred from one random-XOR relay at about 1.9% density. Scaling a **different**, low-bit-flip 128 MiB H100 CPU screen gives about 2.46 s of sequential local staging, detection, packing, codec, apply, and commit per root. It is not a B200→H100 measured cost. |

The 240 MB size and 2.46 s local cost came from different data patterns. Nonexpert weights, full-model batching, receiver fan-out, and useful-work overlap are absent. Because the same-pair TCP rate changed sharply between windows, multiplying a 300 MiB median by full-image bytes would hide the central uncertainty. The [scout's earlier envelope](../cross-zone-transport-2026-09-23/README.md#conditional-one-root-envelope) remains a sensitivity calculation, not a new measurement. The next asynchronous Grug experiment must time encoding, staging, installed-byte acknowledgement and accepted rollout work together.

### Two concurrent logical roots at the measured cadence

The [two-lane runner](../../../scripts/run_cross_zone_fanout.sh) launched two independent sender processes on `s90vxs64` and two receiver processes on `gb977f0`. Each lane sent three fresh 300 MiB ordered versions, first over TCP and then through object storage. Both lanes aimed to start versions 17.38 s apart, the median post-warmup step duration in corrected #698. This tests two logical root/receiver pairs sharing one physical host and NIC per zone. It does **not** test separate physical roots or one-to-many receiver fan-out. All 12 receiver SHA-256 acknowledgements matched the separate receiver files. Raw [sender and receiver files](raw/fanout-two-lane/) and the [analysis](raw/analysis.json) preserve each version.

| Method | Slowest acknowledgement after scheduled version, versions 0/1/2 | Start queue at version 2 |
| --- | --- | ---: |
| TCP4 | 24.660 / 33.143 / 41.386 s | 16.807 s on the slow lane |
| Object32 PUT/GET | 1.854 / 1.559 / 1.328 s | <0.001 s |

The slow TCP lane delivered in 24.66, 24.82 and 24.58 s, while the other delivered in 1.57, 1.49 and 1.50 s **at the same time on the same hosts**. In the slow lane, one of four persistent sockets took about 22.7–22.9 s to send its assigned chunks; the other sockets finished in 0.6–1.2 s. All sockets reported zero retransmissions. The split is consistent with per-flow path or transport behavior, but the cause is not isolated: source ports, congestion window, external traffic and route are not captured well enough to diagnose it. TCP and object phases ran sequentially, so their absolute rates can also depend on time. These data show queueing risk under the tested setup; they do not establish an object advantage at every placement or time. Jobs: `/romain/cross-zone-qual-east-fanout-20260923` and `/romain/cross-zone-qual-rno-fanout-20260923`, both terminal success with zero retries. Logical payload was about 5.27 GiB across direct TCP, object PUT and object GET.

The separate [one-to-two runner](../../../scripts/bench_cross_zone_one_to_two.py) sent **one root's version to two logical receivers** on the same physical H100 host. TCP duplicated the 32 chunks to two independent sets of four sockets. Object delivery uploaded the chunks once, then both receivers fetched and hashed the same keys. The timer ended at the slower acknowledgement. All 12 receiver hashes matched both retained receiver files. Three versions per method started on the 17.38 s cadence:

| Method | Slowest acknowledgement, versions 0/1/2 | Queueing |
| --- | --- | --- |
| TCP4 × two receivers | 1.581 / 1.466 / 1.447 s | None observed |
| Object32 PUT once, GET twice | 1.572 / 1.391 / 1.378 s | None observed |

The methods ran in consecutive phases and used different fresh random content, so these three versions are a fan-out behavior check, not a paired ranking. The [raw sender and receiver results](raw/one-to-two/) and [analysis](raw/analysis.json) include each acknowledgement. Jobs `/romain/cross-zone-qual-east-one-to-two-20260923` and `/romain/cross-zone-qual-rno-one-to-two-20260923` succeeded without retries. Logical payload was about 4.39 GiB: 1.76 GiB direct TCP, 0.88 GiB PUT, and 1.76 GiB GET, excluding headers and other traffic. Physical receiver-host fan-out and simultaneous two-root-to-two-receiver cross-product remain unmeasured.

### NCCL controls and applicability

The [NCCL probe](../../../scripts/bench_cross_zone_nccl.py) broadcasts fresh random GPU bytes from rank 1 to rank 0, computes SHA-256 on both ranks, and times from sender-ready until a collective that returns the receiver's verified digest. The task image above synced the `marinskyrl[cuda]` environment with PyTorch `2.13.0+cu132` and NCCL `2.30.7`.

The cross-zone forced-Socket pair `s90vxs64` → `gb977f0` passed five 300 MiB broadcasts. Full [sender and receiver JSON and NCCL logs](raw/nccl-socket/) show `NET/Socket` on `enP6p3s0np0` and `enp90s0np0`, with matching hashes for every version. The sender-ready times were 2.670 s on the first lazy broadcast, then 0.610, 0.623, 0.615 and 0.614 s. The group setup was measured separately, and the receiver began waiting before the sender pod launched. Jobs: `/romain/cross-zone-qual-east-nccl-socket-20260923` and `/romain/cross-zone-qual-rno-nccl-socket-20260923`, both successful with zero retries. This is one 300 MiB **contiguous GPU buffer** on a fixed two-rank group, so it is a capacity observation rather than a chunk-shaped ranking. It does not show 16 roots, dynamic group recovery or installation into the model's tensors.

A second [NCCL Socket run](raw/nccl-chunks/) used the **same ordered 32 chunk lengths** as the host TCP/object probe. Twelve 300 MiB fresh GPU versions passed SHA-256 at both ranks on the same GB200/H100 hosts. The first lazy broadcast sequence took 2.351 s; the 11 warmed sender-to-ack sequences had median 0.497 s and observed range 0.488–0.522 s. The retained logs again show `NET/Socket` on the physical interfaces. Jobs: `/romain/cross-zone-qual-east-nccl-chunks-20260923` and `/romain/cross-zone-qual-rno-nccl-chunks-20260923`; both succeeded without retries. Logical payload was 3.52 GiB one way. These GPU bytes were generated separately from the host-memory paired blocks, and no receiver weight-tensor apply, group reconfiguration or failure recovery was timed. The observed advantage over the 1.2–1.6 s host-memory windows is promising but does not control source/receiver memory placement or host/time variation.

A third [NCCL Socket run](raw/nccl-fanout/) used one GB200 sender rank and two H100 receiver ranks on **two GPUs of one H100 host**. Five fresh 300 MiB versions with the same 32 chunk lengths matched SHA-256 on all three ranks. The first lazy sequence took 2.306 s; the four warmed sender-to-*both*-receiver acknowledgements were 0.555–0.565 s, median 0.558 s. The full logs show cross-zone `NET/Socket` from GB200 rank 2 to H100 rank 0 and local `P2P/CUMEM` from H100 rank 0 to rank 1. That routing can amortize the cross-zone leg when receivers share a host; it is different from sending two TCP copies or serving two object GETs. Jobs: `/romain/cross-zone-qual-east-nccl-fanout-20260923` and `/romain/cross-zone-qual-rno-nccl-fanout-20260923`, both successful without retries. The receiver-visible logical payload was 2.93 GiB; physical cross-zone bytes depend on NCCL's tree. This is a fixed three-rank GPU group on one host pair, not the full 16-root or multi-host receiver mapping. Its 0.558 s warm time is the fastest **observed** small-fan-out delivery here, with the memory-placement and independent-host limits above.

A same-zone forced-IB 1 MiB GPU broadcast also passed with matching SHA-256 `7d531dfe22918efb8b93f4566f6ada6ba20412a7e531b03ce768fe9a9b37d51a`. Both [rank files and full logs](raw/nccl-ib-same-host/) show `NET/IB` on `ibp0`, but Iris placed both ranks on GB200 host `s90vxs64`; this verifies local NCCL/IB selection and checksum delivery, not an inter-host path. The separate perftest control above verified host-memory RDMA between **distinct** GB200 hosts. A full-node reservation to force distinct-host NCCL/IB was submitted as `/romain/cross-zone-qual-east-nccl-ib-distinct-receiver-20260923`, but Kueue could not admit it: 208 of 209 nodes were excluded for GPU availability. It was cancelled before running, and no inter-host NCCL/IB checksum result is claimed. Cross-zone IB remains unqualified pending the provider's supported configuration and a successful low-level result.

## Decision and next test

- **Fastest observed bounded GPU delivery:** NCCL Socket on the fixed GB200 → H100 group took 0.497 s median for 32 ordered chunks to one H100 GPU and 0.558 s median to two GPUs on one H100 host, through their checksum acknowledgements. The second case used one cross-zone Socket leg and local GPU peer transfer. It is qualified for this small fixed group and measured host pair. No dynamic group or actual model-tensor install was tested.
- **Host-memory paths:** TCP and object storage both passed exact receiver checks, but their ordering was unstable across windows on the same hosts. One TCP flow slowed to roughly 23 s without reported retransmissions while concurrent flows remained fast. The source of that slowdown and the selected LOTA origin/cache state are unknown. Do not choose either path as a universal winner from these data.
- **RDMA:** The tested cross-zone `ibp0`/GID 0 host-memory write did not complete. This is an unqualified candidate, not a measured slow path or proof that no supported cross-zone RDMA route exists.

The smallest next asynchronous Grug test is a bounded dense publication from one B200 trainer root to two H100 rollout GPUs on one host, using the already verified static NCCL Socket group and object PUT/GET control. First compare installed BF16 bytes against an independent dense reference over several versions and one rejected/restarted version; keep that oracle outside timing. Then run the same model/data/config and update cadence with verification disabled, counterbalance the two paths, and record sender-ready → all-installed acknowledgements, pause/drain/resume time, stale work and accepted rollout tokens per wall-clock second. This tests whether the measured delivery advantage survives full publication and useful work. A full 16-root, multi-host fan-out or live production change is outside this qualification.
