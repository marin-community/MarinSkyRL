# B200 to H100 cross-zone transport, 2026-09-23

## Decision supported

Use routed host TCP as the simple direct baseline for a later **bounded, live asynchronous Grug trial**. In this one GB200 sender (`cw-us-east-08a`) to one H100 receiver (`cw-rno2a`) experiment, four-stream object delivery through a bucket configured for US-EAST-02A beat this Python TCP path for 128 and 512 MiB buffers, while one TCP stream beat one object stream at 8 and 512 MiB. The result depends on buffer size, concurrency, bucket configuration, and the application implementation. It does not establish a production winner or raw link capacity. An RDMA transport-selection result is recorded below.

This study transfers synthetic, incompressible bytes and checks SHA-256 on both hosts. It does not transfer or apply weights. [#698](https://github.com/marin-community/MarinSkyRL/issues/698) gives the payload context.

## Measured delivery

The clock starts after the sender has formed a buffer and ends when it receives the receiver's digest acknowledgement. Each cell is the median of five matched checksum-verified samples, followed by the minimum and maximum in seconds. TCP is host-addressed, B200 to H100. Object delivery is a fresh-key PUT by B200 and GET by H100 through each node's LOTA endpoint to `marin-us-east-02a`, configured with signing region `US-EAST-02A`.

| 8 MiB | 4 | 1.337 (0.516–1.380) | 0.518 (0.483–1.084) |

At 512 MiB, these medians imply 123 MiB/s for one TCP stream, 79 MiB/s for four TCP streams, 95 MiB/s for one object stream, and 164 MiB/s for four object streams. Four TCP streams were slower than one in this run; its cause was not isolated. The 128 MiB one-stream arms had long tails, despite no observed sender-side TCP retransmits in the direct arm. Five repetitions per condition give a useful warning about variance, not a stable tail quantile or a precise bandwidth limit. The Python socket loops, checksum work, and shared service load are part of these application timings. Socket buffers and TCP window sizes were neither measured nor tuned; at about 56 ms RTT they are plausible constraints. The TCP and boto3 clients also differ. A later trial should measure window state and compare a tuned or native TCP sender before attributing the object advantage to the network route.

The separate 20 connection-and-echo probes had median 113 ms (108–119 ms), including connect and userspace echo; kernel TCP RTT was about 56 ms. One checksum-verified reverse H100 to B200 8 MiB liveness check took 0.743 s; it includes payload generation and is not a matched direction-speed comparison. All 60 main sender rows match receiver rows and both recorded SHA-256 digests. Sender TCP_INFO showed PMTU 9000, send MSS 8948 and zero total retransmits for every measured data socket. The GB200 host `sjtsxs64` used `10.186.213.73` on `enP6p3s0np0`; the H100 host `gb95a00` used `10.168.192.27` on `enp90s0np0`, both at MTU 9000. The host and interface snapshots are in [`raw/main-sender.json`](raw/main-sender.json) and [`raw/main-receiver.json`](raw/main-receiver.json). IB devices were exposed locally, but the route was over private IPv4, and the zones had different fabric labels. These facts alone do not resolve cross-zone RDMA reachability.

For the 512 MiB four-way object arm, medians were 0.057 s to connect the control channel, 0.644 s for the sender's upload phase, 0.588 s from the receiver command to the last successful object HEAD, 1.826 s for the slowest part GET, and 2.417 s from sender upload completion to acknowledgement. The 3.115 s delivery median is authoritative; the components overlap and medians are not additive. The receiver then issued a second GET of the same keys after acknowledgement; its **sequential** warm-read median was 2.823 s for four parts. A warm hit was not proven. The observed S3 response headers contain no per-request cache hit/miss field, and no LOTA cache counters were retained. Each object key was fresh, but all five repeats at a size reused identical content. A prior read of an exact key by this test is excluded; content-based reuse or other LOTA behavior is not. The selected origin, physical route, and cache state remain unknown.

A bounded follow-up used five **different incompressible buffers per size**, matching TCP and object bytes within each repeat, with four streams. It kept the GB200 host `sjtsxs64` and landed on H100 host `g1cc6b2` (`10.168.194.197`) at a later time. All 30 sender/receiver rows and digests match; each size has five distinct SHA-256 values, and no sender-side TCP retransmits were recorded. Its medians (minimum–maximum) were: 8 MiB TCP 1.246 s (0.466–1.598) versus object 0.448 s (0.423–0.895); 128 MiB TCP 2.228 s (0.877–2.517) versus object 1.627 s (1.611–1.701); 512 MiB TCP 3.783 s (1.726–4.067) versus object 2.643 s (1.883–3.084). The four-stream object advantage persisted with unique content at each repeat. The host and time changed, so the difference from the first run cannot be attributed to content reuse. Per-request cache state and physical origin still were not observable. [`raw/unique-sender.json`](raw/unique-sender.json) and [`raw/unique-receiver.json`](raw/unique-receiver.json) retain every sample; `raw/analysis.json` validates and summarizes them.

## Conditional one-root envelope

[#698's corrected production-like Grug summaries](https://github.com/marin-community/MarinSkyRL/blob/2c5aff75f00f6c9b2583559c956446bb0e0f2fda/docs/experiments/sparse-publication-topology-2026-09-20.md) have 20 post-warmup updates per arm. They report 130.862 GB global dense routed experts across 16 unique PP×EP roots, or 8.179 GB per root; sparse median was 7.343 GB global, or 459 MB/root. Median changed-value density was 1.870%, with a 1.427–2.389% range. #698 also measured a single 128 MiB H100 low-bit-flip CPU XOR screen and a separate random-XOR object relay. These supply **sizes and qualified local costs**, not a new cross-zone timing.

[`raw/analysis.json`](raw/analysis.json) and [`scripts/analyze_cross_zone_transport.py`](../../../scripts/analyze_cross_zone_transport.py) produce a deliberately simple one-root envelope. At the observed 1.870% density, a BF16 GPU index/value payload is modeled as 459 MB; interpolation of the one-stream TCP samples gives about 3.92 s for its network delivery. A random-XOR CPU packet is modeled as 240 MB; interpolation of the four-way object samples gives about 2.16 s for network delivery. Scaling the *separate* low-bit-flip 128 MiB local CPU screen sequentially to 8.179 GB gives about 2.46 s. That H100 bucket timer already includes device-to-host staging, CPU detection, packing, compression/decompression, host-to-device staging, receiver apply, and baseline commit. It is a one-node proxy for a future split B200/H100 path; that split's costs, full-model batching, acknowledgement, and useful-work overlap remain unmeasured. The dense one-root image would require sixteen 512 MiB-ish sends; multiplying the single-payload median gives about 66.5 s, with no validated pipeline or fan-out benefit. These figures are sensitivity calculations. They are not measured publication times and must not be added into a production crossover threshold.

The analysis JSON records six densities from 0.1% to 2.4%, source file hashes, sample IDs, p50/p90/min/max, and each limitation. The GPU sparse formula `3 × density × dense BF16 bytes` omits headers and nonexpert tensors. The CPU packet scaling assumes one random-XOR 1.9% sample represents other densities, while its local CPU screen used a low-bit-flip pattern. The latter compresses far better. The TCP interpolation for the sparse packet uses the noisiest cell, 128 MiB with one stream (0.917–10.262 s), so the 3.92 s estimate is particularly fragile. Full-model batching, split-hardware encoding and apply, sender baseline memory, fan-out to vLLM replicas, failure recovery, and actual asynchronous overlap could change the ranking. #698's same-zone NCCL effective rate must not be transplanted onto this route.

## NCCL transport selection and local staging

The bounded two-rank NCCL 2.30.7 probe used one GPU in each zone and a 1 MiB broadcast from GB200 to H100. The paired default attempt selected `NET/IB/.../GDRDMA` on the GB200, including `ibp2`/`ibp3` queue pairs and channel setup. The H100 job failed with a NCCL watchdog error; its [terminal Iris snapshot](raw/nccl-default-receiver-iris.txt) and the [GB200 sender log](raw/nccl-default-sender-live.log) preserve the two observations. Jobs: [`cw-us-east-08a` rank 1](https://iris-cw-us-east-08a.oa.dev/#/job/%2Fromain%2Fcross-zone-nccl-east-paired-20260923) and [`cw-rno2a` rank 0](https://iris-cw-rno2a.oa.dev/#/job/%2Fromain%2Fcross-zone-nccl-rno-paired-20260923). NCCL selecting a local IB device and initializing its communicator did **not** produce a checksum-verified cross-zone RDMA delivery; the failure cause remains unknown. No RDMA bandwidth measurement is reported.

Restricting `NCCL_SOCKET_IFNAME` to the physical host interfaces (`=enP6p3s0np0` and `=enp90s0np0`), setting `NCCL_NET=Socket` and `NCCL_IB_DISABLE=1`, completed the 1 MiB GPU broadcast with matching SHA-256 `fbbab289f7f94b25736c58be46a994c441fd02552cc6022352e3d86d2fab7c83`. Jobs: [`cw-us-east-08a` rank 1](https://iris-cw-us-east-08a.oa.dev/#/job/%2Fromain%2Fcross-zone-nccl-east-verified-20260923) and [`cw-rno2a` rank 0](https://iris-cw-rno2a.oa.dev/#/job/%2Fromain%2Fcross-zone-nccl-rno-verified-20260923). Their [`sender`](raw/nccl-verified-sender-result.json) and [`receiver`](raw/nccl-verified-receiver-result.json) results and [NCCL](raw/nccl-verified-sender-cross-zone-nccl.sjtsxs64.73.log) [logs](raw/nccl-verified-receiver-cross-zone-nccl.gb95a00.80.log) record `NET/Socket`. The first broadcast includes lazy connection setup, so its 1.06/1.28 s rank times are not throughput figures. This Socket control shows that PyTorch/NCCL can communicate over the physical IPv4 path; it does not identify the IB failure cause.

The same script timed five local 128 MiB GPU/host copies. Median GPU-to-pinned-host and GPU-to-pageable-host times were 0.71/0.72 ms on GB200 and 2.45/6.64 ms on H100; pinned-host-to-GPU was 0.65/2.43 ms. These are local staging observations on one node of each type, not cross-zone transfer times or full-model encoding costs. The first pageable copy was slower on both nodes; all individual timings are in the JSON results.

Questions for CoreWeave: Is any supported InfiniBand/RoCE or UCX/NCCL RDMA path available between GB200 hosts in US-EAST-08A and H100 hosts in RNO2A? If so, which interfaces/GIDs, routing and plugin settings are supported? What private VPC throughput and traffic policy should one expect for a host pair and a small fan-out? Can per-request LOTA hit/miss and selected origin/route be observed for the US-EAST-02A bucket from both zones? The next trial should retain dense and GPU sparse as explicit run-level alternatives, add a bounded CPU object path only after the local stages work on B200/H100, and measure exact installed bytes plus accepted rollout work and acknowledgement under real asynchronous cadence.
